# 多用户受理路径性能验证

2026-09-11 在 macOS arm64、Go 1.26.6 上比较基线 `5ce2b41` 与本次实现。使用 Python `http.client`、回环明文 HTTP DoH、保持连接和同一 `blackhole` 应答（IPv4 `192.0.2.53`）。每轮 1,000 个 POST、16 个并发客户端，每种配置测量 3 轮。控制模式使用独立临时数据库，关闭查询明细，用户额度、QPS 与突发量均为 100,000。

下表是各轮对应指标的中位数：

| 场景 | QPS | p50 | p95 | p99 | 三轮错误总数 |
|---|---:|---:|---:|---:|---:|
| 基线 | 7,866.96 | 1.446 ms | 4.688 ms | 6.604 ms | 0 |
| 当前，控制关闭 | 9,271.65 | 1.254 ms | 4.306 ms | 5.992 ms | 0 |
| 当前，控制开启 | 1,097.52 | 13.984 ms | 19.326 ms | 21.121 ms | 0 |

控制开启后三轮实际 `quota.used` 为 3,000。该路径在放行前持久化受理事务，相比控制关闭多出鉴权、额度/QPS 校验、用量写入及统计开销；本次对比没有单独分离各项耗时。

每轮 QPS 波动明显：基线约 5,616／8,523／7,867；控制关闭约 7,804／11,134／9,272；控制开启约 1,054／1,098／2,226。不能据此认定控制关闭提升了性能，也不能把控制开启的 1,097 QPS 当成生产容量。样本短、客户端和服务同机，未测 TLS、HTTP/3、真实上游、长时间负载或目标磁盘。

公开部署前，应在目标服务器和磁盘上用实际 DoH/DoH3 协议做持续负载验证，核对延迟、错误率、持久化用量以及各用户额度和 QPS。严格扣额依赖事务提交；性能调整不能通过跳过落盘、异步补扣或超额放行改变此约束。
